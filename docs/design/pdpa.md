# การคุ้มครองข้อมูลส่วนบุคคล (PDPA) ของระบบบริหารจัดการชมรมบุคลากร

สถานะ: **ยืนยันแนวทางแล้ว (28 ก.ย. 2569)** — ข้อความประกาศของระบบต้องให้ DPO ของมหาวิทยาลัยตรวจก่อนเปิดใช้
เอกสารนี้ไม่ใช่ความเห็นทางกฎหมาย อ้างอิง: นโยบายคุ้มครองข้อมูลส่วนบุคคล มหาวิทยาลัยมหาสารคาม พ.ศ. 2568 และประกาศความเป็นส่วนตัวสำหรับบุคลากร (เวอร์ชัน 1.1, 31 ก.ค. 2568) — https://pdpa.msu.ac.th

## 0. ข้อสรุปที่ยืนยันแล้ว

| เรื่อง | ข้อสรุป |
|---|---|
| ผู้ควบคุมข้อมูล | มหาวิทยาลัยมหาสารคาม (ระบบดำเนินการโดยสโมสรบุคลากร) |
| ประกาศของระบบ | ทำ **ประกาศความเป็นส่วนตัวเฉพาะระบบ** ตามนโยบายมหาวิทยาลัย ข้อ 2 (ประกาศเฉพาะกิจกรรม/บริการ) อ้างอิงนโยบายและประกาศสำหรับบุคลากรของมหาวิทยาลัย |
| ฐานทางกฎหมายหลัก | ประโยชน์โดยชอบด้วยกฎหมาย — สอดคล้องกับประกาศสำหรับบุคลากร ข้อ 4.7 (กิจกรรมของบุคลากร) และ ข้อ 4.10 (ประกาศผู้ได้รับคัดเลือก/บุคลากรดีเด่น) ไม่ใช้ความยินยอมเป็นเงื่อนไขการใช้ระบบ |
| การแจ้ง | ต้องกด **"รับทราบ"** ประกาศก่อนใช้ระบบ (login ครั้งแรก/เมื่อประกาศเปลี่ยนเวอร์ชัน) และบันทึกหลักฐาน |
| ชื่อ-สกุลภาษาอังกฤษ | **เก็บต่อ** — จำเป็นสำหรับออกใบประกาศ/รางวัลเชิดชูเกียรติ (ระบุวัตถุประสงค์นี้ในประกาศ) |
| คำร้องใช้สิทธิ์ (แก้ไข/ลบ/คัดค้าน/ระงับ) | ยื่นต่อ **DPO ของมหาวิทยาลัย** (dpo@msu.ac.th, 0-4371-9800 ต่อ 2344) ระบบไม่ทำกล่องคำร้องเอง แต่ให้ดู/ดาวน์โหลดข้อมูลของตนเองได้ (P2) |

## 1. สรุปสั้น

- **ควรทำ แต่สิ่งที่จำเป็นที่สุดไม่ใช่ "คำยินยอม" เป็นเงื่อนไขการใช้ระบบ** — PDPA มีฐานทางกฎหมายหลายฐาน (มาตรา 24) การบริหารชมรมบุคลากรของมหาวิทยาลัยน่าจะอาศัยฐาน **ภารกิจของหน่วยงาน/ประโยชน์โดยชอบด้วยกฎหมาย** ได้เหมาะกว่า
  - คำยินยอมในความสัมพันธ์นายจ้าง–ลูกจ้างมักถูกมองว่าไม่ได้ให้โดยอิสระ
  - ผู้ใช้ถอนความยินยอมได้ทุกเมื่อ (มาตรา 19) ถ้าระบบอาศัยความยินยอมเป็นฐานหลัก การถอนจะทำให้ต้องหยุดประมวลผลข้อมูลที่จำเป็นต่อการทำงานของชมรม
- **สิ่งที่ต้องมีไม่ว่าจะใช้ฐานใด: การแจ้งประกาศความเป็นส่วนตัว (Privacy Notice) ก่อนหรือขณะเก็บข้อมูล (มาตรา 23)** — ระบบยังไม่มีเลย เป็นช่องว่างหลัก
- **คำยินยอมใช้เฉพาะการประมวลผลที่ "ไม่จำเป็น" ต่อการใช้บริการ** (ให้ผู้ใช้เลือกได้และถอนได้โดยไม่เสียสิทธิ์ใช้ระบบ)
- ข้อเท็จจริงสำคัญ: **ระบบไม่ได้เข้าถึงกล่องอีเมล (Gmail) ของผู้ใช้** — ใช้ Google เพื่อยืนยันตัวตนเท่านั้น และส่งอีเมลแจ้งเตือนจากบัญชีสโมสร (staff.club) ที่มีสิทธิ์ "ส่ง" อย่างเดียว

## 2. ข้อมูลส่วนบุคคลที่ระบบประมวลผล (ข้อเท็จจริงจากโค้ด)

| กลุ่มข้อมูล | ข้อมูล | แหล่งที่มา | วัตถุประสงค์ | ใครเห็น | ระยะเวลาเก็บปัจจุบัน |
|---|---|---|---|---|---|
| บัญชีผู้ใช้ | Google ID (`sub`), อีเมล, ชื่อ, URL รูปโปรไฟล์, เวลาเข้าใช้ล่าสุด | Google (scope `openid email profile`) ตอน login | ยืนยันตัวตน, แสดงชื่อ/รูป | ผู้ใช้ที่ login (ชื่อ/รูปในรายชื่อชมรม) | ไม่มีกำหนด (ปิดบัญชีด้วย `is_active`) |
| ข้อมูลบุคลากร | รหัสบุคลากร, คำนำหน้า/ชื่อ-สกุล **ไทยและอังกฤษ**, ตำแหน่ง, คณะ/หน่วยงาน/หลักสูตร (ชื่อและรหัส ERP) | ERP-HR ของมหาวิทยาลัย (เรียกด้วย access token ของผู้ใช้เองตอน login) | ระบุตัวบุคลากร, สังกัด, เอกสารชมรม | ตัวเอง, กรรมการชมรม, เจ้าหน้าที่สโมสร | อัปเดตทุกครั้งที่ login ไม่มีกำหนดลบ |
| ข้อมูลนิสิต | รหัสนิสิต, คณะ | อนุมานจากอีเมล | แยกประเภทบัญชี | ตัวเอง | ไม่มีกำหนด |
| ชมรม | สมาชิกภาพ, ตำแหน่งกรรมการ, **เบอร์โทรติดต่อ**, สถานที่ทำงาน, ประวัติย่อ (bio) | ผู้ใช้กรอกเอง | บริหารชมรม, เอกสารตามแบบฟอร์มสโมสร | เบอร์โทร: เฉพาะผู้มีสิทธิ์ภายในชมรม; เอกสารพิมพ์ | ไม่มีกำหนด (บันทึกทางการ) |
| กิจกรรม/ผลงาน | การเข้าร่วมกิจกรรม, ผลงาน, ผลการแข่งขัน/สถิติกีฬา, ผลการคัดเลือก + เหตุผล | ผู้ใช้/กรรมการบันทึก | บริหารชมรม, คัดเลือกตัวแทน/รางวัล | ตามสิทธิ์; ประกาศผลคัดเลือกเห็นทุกคนที่ login | ไม่มีกำหนด |
| ไฟล์ | รูปกิจกรรม (อาจมีใบหน้าบุคคล), หลักฐานผลงาน, ใบคำยินยอมที่ปรึกษาภายนอก | ผู้ใช้อัปโหลด | หลักฐาน/ประวัติชมรม | ตามสิทธิ์ของข้อมูลต้นทาง | ไม่มีกำหนด |
| บุคคลภายนอก (ที่ปรึกษา) | ชื่อ, หน่วยงาน, ตำแหน่ง, อีเมล/เบอร์โทร | ผู้ยื่นคำขอกรอก | ที่ปรึกษาชมรม | ผู้เกี่ยวข้องกับคำขอ/ชมรม | ไม่มีกำหนด |
| อีเมลแจ้งเตือน | อีเมลผู้รับ, หัวเรื่อง, เนื้อหา | ระบบสร้าง | แจ้งเตือนงานที่เกี่ยวข้อง | super_admin (หน้าตั้งค่าอีเมล) | **90 วัน** |
| session | token (เก็บเป็น hash), เวลาใช้งาน | ระบบ | รักษาการ login | — | 7 วัน |
| สำรองข้อมูล | ทุกอย่างข้างบน + ไฟล์ env (secret) | ระบบ | กู้คืน | ผู้ดูแลเซิร์ฟเวอร์ | **14 วัน** (ยังไม่มีสำเนานอกเครื่อง) |

ข้อมูลที่ **ไม่เก็บ** (ตั้งใจแล้ว): เบอร์โทรจาก ERP, ข้อมูลสุขภาพของนักกีฬา, รหัสผ่าน, token ดิบ, Google access token (ใช้แล้วทิ้ง), เนื้อหาอีเมลในกล่องของผู้ใช้
ข้อมูลอ่อนไหว (มาตรา 26): **ไม่มี** ในปัจจุบัน — ต้องระวังถ้าเพิ่มในอนาคต (สุขภาพ, ศาสนา, ความพิการ ฯลฯ ต้องขอความยินยอมโดยชัดแจ้ง)

## 3. วิเคราะห์ฐานทางกฎหมาย (ให้ DPO ยืนยัน)

| การประมวลผล | ฐานที่เสนอ (มาตรา 24) | เหตุผล |
|---|---|---|
| Login ด้วย Google, บัญชีผู้ใช้ | ภารกิจ/ประโยชน์โดยชอบด้วยกฎหมาย | จำเป็นเพื่อให้บริการระบบของมหาวิทยาลัยแก่บุคลากร |
| ดึงข้อมูลบุคลากรจาก ERP-HR | ภารกิจ/ประโยชน์โดยชอบด้วยกฎหมาย | ใช้ข้อมูลภายในหน่วยงานเดียวกัน เพื่อยืนยันสถานะบุคลากรและสังกัด — ต้องแจ้งในประกาศ และเก็บเท่าที่จำเป็น |
| บริหารชมรม, สมาชิก, กรรมการ, เอกสารตามแบบฟอร์ม | ภารกิจ / สัญญา (การเป็นสมาชิกชมรม) | ผู้ใช้สมัครหรือรับตำแหน่งเอง |
| อีเมลแจ้งเตือนงาน (ที่ปรึกษา, ผลคำขอ, คิวงาน) | ประโยชน์โดยชอบด้วยกฎหมาย | เป็นการแจ้งเรื่องที่ผู้รับต้องดำเนินการ ไม่ใช่การตลาด |
| ประกาศผลคัดเลือก (ชื่อ + เหตุผล) | ภารกิจ | ความโปร่งใสของการคัดเลือก — ควรระบุในประกาศ และจำกัดเหตุผลให้เป็นข้อเท็จจริงด้านผลงาน |
| รูปกิจกรรมที่เห็นใบหน้า | ประโยชน์โดยชอบด้วยกฎหมาย (+ แจ้งในงาน) | แนวปฏิบัติทั่วไปของหน่วยงาน; ภาพเผยแพร่ภายนอกควรพิจารณาแยก |
| ข้อมูลที่ปรึกษาภายนอก | ประโยชน์โดยชอบด้วยกฎหมาย / ความยินยอม (ในใบคำยินยอมอยู่แล้ว) | ไม่ได้เป็นผู้ใช้ระบบ ต้องแจ้งผ่านเอกสารที่ลงนาม |

**ทำไมไม่ใช้ "ความยินยอม" เป็นเงื่อนไขเข้าใช้ระบบ**
1. ความยินยอมต้องให้โดยอิสระ (มาตรา 19) — ถ้าไม่ยินยอมแล้วใช้ระบบชมรมไม่ได้ ถือว่าไม่อิสระ
2. ถอนได้ทุกเมื่อ — ระบบต้องหยุดใช้ข้อมูลนั้นทันที ซึ่งขัดกับการเก็บบันทึกทางการของชมรม
3. ถ้าใช้ฐานอื่นได้อยู่แล้ว การขอความยินยอมซ้อนจะทำให้ผู้ใช้เข้าใจผิดว่าตัดสิทธิ์ได้

## 5. แนวทางปรับปรุง (แบ่งระยะ)

### ระยะ P1 — แจ้งประกาศความเป็นส่วนตัว (แก้ G1) ★ ทำก่อน
- **หน้า `/privacy` (public)** — ประกาศความเป็นส่วนตัวของระบบ ตามหัวข้อที่มาตรา 23 กำหนด: ผู้ควบคุมข้อมูล (มหาวิทยาลัย/สโมสรบุคลากร), ข้อมูลที่เก็บและแหล่งที่มา (ตารางหัวข้อ 2), วัตถุประสงค์และฐานทางกฎหมาย, ผู้รับข้อมูล, ระยะเวลาเก็บ, สิทธิของเจ้าของข้อมูล, ช่องทางติดต่อ DPO
  - เนื้อหาจัดทำร่วมกับ DPO และอ้างนโยบายคุ้มครองข้อมูลส่วนบุคคลของมหาวิทยาลัย
  - ลิงก์จาก landing page, หน้า login และ footer ทุกหน้า
- **การรับทราบ (acknowledgement) ไม่ใช่ความยินยอม**: login ครั้งแรก หรือเมื่อประกาศเปลี่ยนเวอร์ชัน → แสดงประกาศพร้อมปุ่ม "รับทราบ" แล้วจึงใช้งานต่อ
  - ตาราง `privacy_notice_acknowledgements` (`user_id`, `notice_version`, `acknowledged_at`, UNIQUE(`user_id`, `notice_version`)) — หลักฐานว่าแจ้งแล้ว
  - เวอร์ชันประกาศเป็นค่าคงที่ในโค้ด เปลี่ยนสาระสำคัญ = เพิ่มเวอร์ชัน = ทุกคนเห็นอีกครั้ง
- **ข้อความสั้นที่จุดเก็บข้อมูล** (just-in-time notice): ฟอร์มกรอกเบอร์โทรกรรมการ, อัปโหลดรูปกิจกรรม, กรอกข้อมูลที่ปรึกษาภายนอก — บอกว่าใครจะเห็น
- **ใบคำยินยอมของที่ปรึกษาภายนอก**: เพิ่มข้อความแจ้งการเก็บข้อมูล (แก้ G7)

### ระยะ P2 — สิทธิของเจ้าของข้อมูล (แก้ G2)
- **หน้า "ข้อมูลของฉัน"** (`/settings/my-data`): แสดงข้อมูลทั้งหมดของผู้ใช้แยกตามกลุ่มในหัวข้อ 2 พร้อมแหล่งที่มาและผู้ที่เห็นได้
  - **ดาวน์โหลดสำเนา** (JSON) — สิทธิขอรับสำเนา/โอนย้าย
  - ข้อมูลจาก ERP: แสดงวันที่ซิงก์ และแนะนำให้แก้ที่ต้นทาง (งานบุคคล) — ระบบจะอัปเดตเองเมื่อ login ครั้งถัดไป
- **คำร้องใช้สิทธิ์**: ยื่นต่อ DPO ของมหาวิทยาลัย (ข้อสรุปหัวข้อ 0) — หน้า "ข้อมูลของฉัน" แสดงช่องทางติดต่อ DPO และบอกว่าข้อมูลแต่ละกลุ่มแก้ไขที่ใด (ERP → งานบุคคล, ข้อมูลชมรม → กรรมการชมรม)
  - การลบมีข้อยกเว้น: บันทึกทางการของชมรม (คำขอที่อนุมัติ, รายงาน, ผลคัดเลือก) เก็บต่อ — ใช้การปิดบัญชี/ลดทอนการระบุตัวตนแทนการลบ (ดำเนินการตามคำสั่ง DPO)

### ระยะ P3 — ลดข้อมูลและกำหนดระยะเวลาเก็บ (แก้ G3, G4)
- **นโยบายระยะเวลาเก็บ** (ตัวเลขให้ DPO/สโมสรกำหนด) และงานอัตโนมัติ เช่น
  - บัญชีที่ไม่ได้ login เกิน N ปี หรือพ้นสภาพบุคลากร → ลบข้อมูล ERP (`staff_profiles`) และ URL รูปโปรไฟล์ คงชื่อไว้ในบันทึกทางการ
  - session หมดอายุ → ลบแถว (ไม่ใช่แค่หมดอายุ)
- ทบทวนข้อความ "เหตุผล" ในประกาศผลคัดเลือกให้เป็นข้อเท็จจริงด้านผลงานเท่านั้น

### ระยะ P4 — การดำเนินงาน (แก้ G5, G6)
- สำรองข้อมูลนอกเครื่อง **เข้ารหัสก่อนส่ง** (เช่น `age`/`gpg` ใน `backup.sh`) และจำกัดสิทธิ์ปลายทาง
- `docs/pdpa/ropa.md` — บันทึกรายการกิจกรรมการประมวลผลตามหัวข้อ 2–3
- `docs/pdpa/breach-response.md` — ขั้นตอนเมื่อข้อมูลรั่วไหล: ระงับ → ประเมิน → แจ้ง DPO → แจ้ง สคส. ภายใน 72 ชม. (ถ้ามีความเสี่ยง) → แจ้งเจ้าของข้อมูล (ถ้าเสี่ยงสูง)

### ความยินยอม (เฉพาะเมื่อมีการประมวลผลที่ไม่จำเป็น)
ปัจจุบันยังไม่พบการประมวลผลที่ต้องอาศัยความยินยอม ถ้าอนาคตมี (เช่น เผยแพร่รูป/ผลงานบนเว็บไซต์สาธารณะ, จดหมายข่าวกิจกรรม) ให้ทำระบบความยินยอมแยกวัตถุประสงค์:
- ตาราง `user_consents` (ผู้ใช้, วัตถุประสงค์, ให้/ถอน, เวอร์ชันข้อความ, เวลา) แบบบันทึกต่อท้าย (แก้/ลบไม่ได้) เพื่อเป็นหลักฐาน
- ถอนได้ในหน้า "ข้อมูลของฉัน" ง่ายเท่ากับตอนให้ และการถอนไม่กระทบการใช้ระบบส่วนอื่น

## 6. สิ่งที่ยังรอ

1. DPO ตรวจข้อความประกาศของระบบ (`apps/web/src/components/privacy/PrivacyNotice.tsx`) ก่อน deploy
2. ระยะเวลาเก็บบัญชีและข้อมูล ERP ของผู้พ้นสภาพ (P3) — ประกาศสำหรับบุคลากร ข้อ 8 ระบุว่าเก็บตลอดการจ้างงานและบางส่วนเก็บถาวร ต้องให้ DPO กำหนดสำหรับระบบนี้
